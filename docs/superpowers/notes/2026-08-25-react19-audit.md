# React 19 compatibility audit — M3 Task 1

**Verdict: GO.** Every React-coupled dependency at its *installed* version already
declares React 19 support. No upgrades are required before scaffolding Next.js 15,
and the Next 14 / React 18 fallback is not needed.

Audited 2026-08-25 against the resolved tree (`npm ls --depth=0`), not the
`package.json` ranges. That distinction mattered: two entries look unsupported by
their declared range and are fine in practice.

| `@tiptap/react` | `^3.22.5` | 3.22.5 | `^17.0.0 \|\| ^18.0.0 \|\| ^19.0.0` | OK |

## The trap this avoided

`@tanstack/react-query@5.51.0` and `@testing-library/react@16.0.1` — the versions
the ranges name — declare `react: ^18.0.0` only. Reading `package.json` alone would
have produced a false blocker and sent this milestone down the Next 14 path for no
reason. The caret ranges have already resolved past both: 5.90.21 and 16.3.2 respectively.

The inverse risk is real too. A fresh `npm install` on a clean machine resolves to
whatever satisfies the caret *then*, which is not necessarily what is in the lockfile
now. `package-lock.json` is what makes this audit reproducible, so it must stay
committed and must not be regenerated casually during the migration.

## What this does not cover

Peer declarations are a claim of support, not proof of it. Two things stay unproven
until the code actually runs on React 19:

- **Tiptap under StrictMode.** Editors that attach to a DOM node are the classic
  casualty of React 19's stricter double-invocation. Task 6 ports `/cv` last for
  exactly this reason.
- **`@testing-library/react` with the new `act`.** The 299-test suite passing after
  the upgrade is the real signal; Task 2 Step 7 checks it.

If either breaks, the failure is local to that surface and does not invalidate this
verdict — fix forward rather than reverting the framework.
